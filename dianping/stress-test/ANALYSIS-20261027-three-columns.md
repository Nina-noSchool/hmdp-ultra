# 三列 R1 对照（2026-10-27，预热增强版）：JDK8 / JDK21 平台线程 / JDK21 虚拟线程

> 本文是预热增强版结论，取代同日早些时候的无预热数据（见文末"历史轮次"）。
> 六轮全部 4000/4000、HTTP 0 错误、三方数字咬合、`一致性判定: YES`。

## 环境与方法

- VM：4 vCPU / 11.7G，MySQL、Redis、RocketMQ、Prometheus 与应用同机，JMeter 也在 VM 上。
- 参数：4000 并发、3s 爬坡、券 13、Hikari 20、`com.hmdp=INFO`、
  `send-message-timeout=10000`；每列 `REPEATS=2` 轮。
- 每轮流程：停应用 → preclean（清压测券+预热券数据、清本地消息表）→
  reset broker + 启停一次应用消费尾部消息 → prepare → 启动应用（benchmark profile）→
  **seckill 预热（独立券 999 × 300 单，顺序）** → 商详预热 → JMeter → 消费收敛 → 断言。
- 索引补丁与预热券种子 SQL 均已应用。
- 索引补丁已应用：`tb_voucher_order(voucher_id/create_time)`、
  verify/recovery(voucher_id)、reconcile log(log_type, create_time)。

## 为什么必须预热

同日早些时候无预热的 col1（JDK8）两次冷启动都是 3200/4000：Tomcat 800 个工作线程
被 4000 并发冲激全部压到第一批 `syncSend` 上，800 单发送超时回滚（HTTP 仍是 200）。
预热增强版引入独立预热券后，同样冷启动的 col1 两轮 `MQ发送超时` 从 **800 → 1**，
4000/4000 全部一致。预热把"第一波"伤害转移到了正式压测之前。

两个值得记录的现象：

1. **`jvm_threads_live` 在虚拟线程模式下不升反降（306 → 198）**。
   虚拟线程不计入 `jvm_threads_live`（它只统计平台线程）；虚拟模式下 Tomcat 的

## 结论

1. **虚拟线程在当前实现下没有吞吐收益，延迟被放大一个数量级。**
   同 jar 同参数只切开关：吞吐 140 vs 145（-3~-4%，接近噪声）；
   Avg 440-531ms vs 45-47ms（约 10 倍）；P50 218-444ms vs 26-27ms（约 8-16 倍）。
   四个总样本（含无预热轮）方向完全一致。

2. **机制（Phase D 实证后的修正版）：队列从 Tomcat accept 队列移进了处理管线内部。**
   先给证据，再给解释：

   **证据 A：延迟是服务端真实的，不是测量伪影。**
   Prometheus `http_server_requests` 加权平均（整窗 increase 比值）：
   col1=33.3ms、col2=32.1/31.7ms、col3=**350.1/411.0ms**（JMeter 同轮 42/45/439-531ms）。
   服务端自己就慢了 10 倍。

   **证据 B：顺序单发完全健康。**
   压测后在同一虚拟模式实例上顺序 POST 12 次，单请求走完
   Lua + 2 次 syncSend + verify INSERT 全链路只要 **4-6ms**。
   100 倍劣化是纯并发效应，不是代码路径变慢。

   **证据 C：pinning 不是问题（R-1 排除）。**
   JFR `jdk.VirtualThreadPinned` 全程仅 76 次、单次 12-117ms，
   栈为 `parkOnCarrierThread`（带监视器停车），量级可忽略。

   **证据 D：没有慢 I/O。**
   JFR `jdk.SocketRead`（profile 配置，阈值 10ms）1048 次慢读全部是
   MySQL 驱动（消费侧行锁等待为主），RocketMQ 与 Redis 的慢读为 **0**；
   ~8000 次 `syncSend` 里请求线程实际 park 在 `CountDownLatch2` 上只有 **20 次**
   —— 本地 broker 响应快到调用线程几乎不等。

   **证据 E：CPU 不饱和。**
   JFR 执行采样 90 秒仅 ~1160 个样本（约 12-23 秒 CPU），热点高度分散
   （HashMap/String/MyBatis 反射/mysql 驱动 SQL 解析）；JVM 线程数虚拟模式
   平台线程 306→198（Tomcat 工作线程虚拟化，`jvm_threads_live` 不计虚拟线程）。

   **与全部证据一致的解释**：平台线程模式下，Tomcat 的 800 线程上限 + accept
   队列把"在应用里并发执行"的请求数压到 ~5 个（到达率 145/s × 32ms 服务时间），
   排队发生在 accept 队列——不进服务端计时。虚拟模式放行所有连接，同一时刻
   管线内部挤着几十个各等下一个异步跳板的请求：每个请求要经过 Tomcat 分发、
   3 次 lettuce 命令、2 次 MQ 发送、响应回写等多个"完成-再调度"跳板，
   每个跳板都要与 RocketMQ 客户端内部线程（park 统计中 NettyClientPublicExecutor
   9626 次、消费者线程 8101 次停车的大户）、消费端、HTTP 回写共享仅 4 个 CPU。
   队列没有消失，而是从 accept 队列搬进了管线内部的各级执行器——
   每跳的排队延迟叠加成 350-411ms。吞吐不变，因为稳态闸门仍是消费端 ~145/s。

   这一解释与"carrier 饥饿""pinning""慢 I/O"等简单假说都不矛盾地共存，
   但精确到每一跳的延迟分解需要 JFR 方法级分析或分段计时（Filter 埋点），
   属于后续工作（见"下一步"）。

3. **JDK8 老栈本身不慢，冷启动才是敌人。**
   预热后 col1 吞吐中位 138.7/s，与 col2 的 145 同档（-4%）；此前的"800 超时"
   纯粹是冷 JVM 第一波效应，不能作为"JDK8 vs JDK21"的运行时结论。

4. **质量增强手段全部有效。**
   - 预热券隔离 + 预热后断言：col1 从两轮全废到两轮全过；
   - `MQ发送超时` 计数进 summary：1 次残留超时可见，而不是靠翻日志；
   - 每轮完整 preclean/reset/drain 循环：六轮之间零污染；
   - 三方断言 + `一致性判定`：六轮全部通过，数据可信。

## 默认开关决策

**保持 `concurrency.virtual-threads.enabled=false`。**

在"请求路径同步 syncSend + 异步 DB 消费"的现有架构下，虚拟线程既无吞吐收益，
又因移除线程池背压把延迟放大 10 倍。负结果 + 机制解释本身就是完整结论。
若未来想让虚拟线程发挥价值，方向是给请求路径加显式限流/排队
（恢复背压）或把 syncSend 改为异步化，属于架构级改动，不在本实验范围。
